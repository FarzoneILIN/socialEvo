 # SocialEvo 最小原子实验

最小原子实验：两个 Agent，各自拿到一半线索，看它们能不能通过对话把信息拼起来、找出正确答案。跑完会留下完整的轨迹日志和评分。

**它的作用是验收基础设施。** 一个任务族、两个条件，目前只能回答"环境、日志、评分这条路通不通"。

不接 API 也能跑（用离线的脚本策略），接了 API 就能换成真模型。

\---

## 先跑起来

只依赖标准库，Python 3.10+。在 `code/atomic_exploration/` 下执行：

```powershell
python -m unittest discover -s atomic_experiment/tests -v
python -m atomic_experiment --backend mock --instances 2 --repeats 2
```

`mock` 是写死的程序策略，不调模型、不花钱，走的是和 LLM 完全相同的观测入口（也一样看不到标准答案）。它用来验管线，**它跑出来的分数不是实验结果，不能写进报告里。**

`--help` 能看全部参数。

## 任务是怎么设计的

16 个没有语义的候选 ID。每个 Agent 私下拿到 4 个候选，两份线索的交集恰好是唯一正确答案——也就是说，**谁都无法只靠自己的线索唯一确定答案；交换信息后才能确定唯一答案。**

两个条件：`comm` 允许发消息，`no_comm` 禁止。同一批任务、同一个模型、同一个预算上限，但不强制两边实际花掉一样多。

每轮两个 Agent 先各自基于轮初状态做决定，收齐了再一起执行，消息下一轮才看得到。API 请求是一个个发的，但环境语义上是同步的。 合法动作只有三个：`send`、`submit`、`wait`。一次调用只能做一个动作，提交了不能改，过程中不告诉它答没答对。

主指标是**两个 Agent 都答对**的团队成功率。另外记个体准确率、调用次数、接口报告的 token、非法动作次数和耗时。

**这个任务是故意设成信息互补的**，所以就算 `comm` 赢了，也只能说明“在当前协议与预算设置下，开放通信通道的完整流程表现更好”。由于两组实际调用次数可能不同，增益还不能完全归因于信息交换，更证明不了自组织、动态重组，或者哪种组织结构更好。不能过度解读。

## 代码结构

|文件|作用|
|-|-|
|`config.py`|配置和预算检查|
|`environment.py`|出题、私有观测、动作校验、客观评分|
|`../utils/client.py`|公共模型接口，可替换；默认走离线脚本|
|`runner.py`|隔离历史、同步轮次、两个条件配对跑、汇总|
|`recording.py`|逐步 JSONL 日志 + JSON 结果|
|`__main__.py`|命令行入口|

要换模型接口可修改公共模块 `utils/client.py`，环境和评分不用动。

## 接 API

目前支持 Bearer 认证 + Chat Completions 风格的 JSON 接口。别的协议要改 `utils/client.py`。

```powershell
$env:SOCIALEVO_BASE_URL = "https://你的服务商地址/v1"
$env:SOCIALEVO_MODEL = "实际模型名"
$env:SOCIALEVO_API_KEY = [System.Net.NetworkCredential]::new("", (Read-Host "API Key" -AsSecureString)).Password
python -m atomic_experiment --backend api --instances 1 --repeats 1
```

BASE_URL 结尾不要带 `/chat/completions`。不会自动读 `.env`。

上面这种输入方式不会把密钥写进命令历史，但进程跑着的时候它还在环境变量里。

如果服务商要求另一种受支持的参数名，可以使用 `--token-parameter max_completion_tokens`；目前只支持 `max_tokens` 和 `max_completion_tokens`。

**第一次真跑务必加 `--instances 1 --repeats 1`**，这样最多 16 次请求。参数、推理 token 怎么算、usage 字段长什么样，这些都得拿真实接口验一遍——我这边只验到离线和本地模拟 HTTP，还不知道API是不是都兼容**。**

## 开销和出错规则

每个条件每次重复默认最多 4 轮、8 次请求，单次输出上限 256。**非法动作照样扣请求额度，不给免费重试。**

整批的请求上限是 `2 × instances × repeats × min(max_calls, 2 × rounds)`。

累计报告 token 超过 12000 就不再发新请求。注意这是**收到响应之后才判断的软阈值**——最后一次请求可能已经超了。它不是硬性费用上限，也不保证服务商真的执行了你要求的输出上限。

出错就停整批：`usage.total_tokens` 缺失、HTTP 错误、网络错误，任何一个都停。**已经发出去的请求可能已经产生费用了，不能当成零消耗。** 没有自动重试；改完配置重跑会生成一个新目录，不会覆盖。

统计口径：网络失败和 usage 缺失不进准确率的分母；非法动作、轮次用完、预算耗尽导致没作答，算失败。汇总里同时保留尝试数和可评估数。

## 结果位置

每次运行新建一个 `atomic_experiment/runs/<UTC时间_随机ID>/`：

* `manifest.json` — 配置、模型、系统提示词、代码哈希
* `events.jsonl` — 每次的实际输入、原始输出、动作、状态、用量、耗时
* `i*_r*_*.json` — 每个任务 × 重复 × 条件的结果
* `summary.json` — 两组汇总、配对准确率差、有没有中断

日志是研究者视角的，**里面有两份私有线索和标准答案**。模型只拿到自己那份观测和合法收到的消息。**不能把完整日志倒回去喂给 Agent 当上下文**，那就泄题了。

日志会把当前密钥的精确字符串替换掉，但它不是通用的脱敏器，别指望它能兜住别的敏感信息。

## 验收顺序

1. 测试通过
2. mock 下两个条件都能跑完
3. 真实接口下能跑通一对任务
4. **手工翻一遍轨迹**：私有信息有没有泄漏、动作对不对、评分对不对
5. 确认没问题再加大 instances

**还没有扩任务族，也没有加上干预实验。** 这一版的目的只是把管线验证清楚。
